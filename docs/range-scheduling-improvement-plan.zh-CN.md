# HTTP Range 动态区间调度改进方案

日期：2026-09-13。状态：P0/P1/P2 主体已实施，P3 的可复现实验入口已补齐；默认策略已切换为 Dynamic，公网性能对照作为持续观测记录。本文件替代此前以固定 batch 调参为主的方案，并持续记录设计与验收要求。

目标：保留 piece 作为进度、校验与断点单位，按未完成连续区间和实际请求槽位动态决定 HTTP 请求范围。固定 batch 保留为兼容模式和性能对照；8 MiB 不作为 aria2 默认值，也不预设为最优值。

## 1. 现状与依据

### 当前实现

- `piece_size` 默认 1 MiB，`request_batch_size` 字段默认 4 MiB；默认 Dynamic 使用独立的动态范围限制，Fixed 模式保留静态合并上限，不随速度或剩余工作自动调整。
- 普通请求现在在一次 scheduler 锁内原子领取首 piece 与后续 batch，消除首片和扩批之间的竞争窗口；`extend_batch` 仍保留为受测的底层兼容辅助接口。
- 固定扩展只合并连续、未触碰的完整 piece，受字节上限、64 个 lease 上限、区间占用、文件末尾和实际已占用请求槽位限制。
- 固定模式按已占用的 HTTP 请求计算剩余槽位，不再无条件为其他 `max_connections - 1` 个 worker 固定预留区间；动态模式另按连续候选区间和虚拟槽位分配。
- 固定模式中 `request_batch_size=0` 关闭合并；小于 piece 的值不切小该 piece。它仅适用于已知长度的多连接 Range 下载。

入口：[config.rs](../src/config.rs)、[scheduler.rs](../src/scheduler.rs)、[adaptive.rs](../src/session/multi/adaptive.rs)。

### aria2 的借鉴点

以 aria2 1.37.0 普通 HTTP 下载为参照：

| 概念 | 行为 |
| --- | --- |
| piece | 默认 1 MiB，提供分割对齐边界，不等于每次 HTTP 请求长度 |
| `min-split-size` | 默认 20 MiB，小于两倍该值的区间不继续拆分；它不是请求长度 |
| 默认选择器 | 查询未完成、未使用的连续区间；相邻位置已有下载者时考虑从中间选取，比较候选区间并检查拆分门槛 |
| HTTP 请求 | 非 pipelining 路径支持显式结束位置，也支持开放终点；调度区间与线上 Range 要分别观察 |

来源：[官方手册](https://aria2.github.io/manual/en/html/aria2c.html)、[默认选择器](https://github.com/aria2/aria2/blob/release-1.37.0/src/DefaultStreamPieceSelector.cc)、[区间选择源码](https://github.com/aria2/aria2/blob/release-1.37.0/src/BitfieldMan.cc#L229)、[HTTP 请求源码](https://github.com/aria2/aria2/blob/release-1.37.0/src/HttpRequest.cc#L90)。

约 64 MiB 文件在 8 连接下出现约 8 MiB 区间，可以用逐步拆分和 piece 对齐解释，但不是固定公式。本方案借鉴其连续区间选择思想，不声称复刻 aria2 的全部调度和连接接续行为。

### 已有实验摘要

同一 ZIP 为 64,469,455 字节，约 61.48 MiB，SHA-256 为 `2132eda841919e4de7c8a77a0a47ab9f117310a785562905b932bebc141c2c7c`。环境为 Windows、IPv4、vendored libcurl + Schannel，对照 aria2 1.37.0。

| 运行 | 配置 | 8 连接 bytehaul 中位耗时 | aria2 中位耗时 |
| --- | --- | --- | --- |
| `20260913-014608` | 固定 4 MiB | 4.706 s | 2.538 s |
| `20260913-015821` | 临时固定 8 MiB | 5.584 s | 8.380 s |

4 MiB 运行的 bytehaul 请求数为 26、22、26，aria2 约 17、16、15；8 MiB 运行的 bytehaul 每轮 17 个 Range 请求，aria2 记录 17、17、18 个 HTTP 响应。请求数和响应数口径不能混用。

两次运行各包含 1/8 连接、每组 3 轮，分别 12/12 次通过跨工具 SHA-256 一致性和 ZIP CRC。没有发布方可信摘要，结论限于产物一致且 ZIP 内容完整。aria2 显式使用 `--min-split-size=1M --piece-length=1M` 并按组设置连接数，不是默认配置。

两组不在同一时间窗口，受 CDN、路由与慢请求影响，不能认定 8 MiB 稳定提速，也不能把全部耗时差归因于 Range 大小。

原始报告：[4 MiB](../target/public-compare/20260913-014608/report.md)、[8 MiB](../target/public-compare/20260913-015821/report.md)。`target` 可能被清理，后续须归档命令、配置、逐轮结果、诊断和构建身份。

## 2. 范围与兼容性

第一版已改变已知长度多连接下载中普通新请求的分配。保持有限终点 Range、现有 probe 精确接管、流式 body 和逐 piece 持久化。恢复后缀、已触碰 piece 和断点空洞保留专用路径。

已新增显式模式及 Rust/Python 配置 API：

| 模式 | 语义 |
| --- | --- |
| `dynamic` | 默认根据空闲区间和实际槽位分配请求，使用独立的范围限制 |
| `fixed` | 显式启用，保留 `request_batch_size` 全部语义 |

动态模式不复用 `request_batch_size=0` 表示自动。该字段在动态模式不参与计算，应在 Rust/Python 文档和有效配置诊断中明确展示，避免用户以为仍受固定 batch 限制。

动态模式已增加独立的最小拆分长度与最大请求长度配置，不改变现有 `min_split_size` 含义；配置、绑定和验证规则已同步。最小拆分长度按 piece 对齐，最大请求长度小于 piece 时仍允许下载一个 piece。

第一版沿用每请求最多 64 个 piece lease 的资源边界，1 MiB piece 下有效上限约 64 MiB，必须在诊断中显示。若该限制成为瓶颈，再设计区间所有权与逐步创建 lease，不直接取消上限。中断请求的当前部分消费 piece 与尚未消费的连续后缀分开恢复：前者保留精确剩余范围，后者按原 lineage/退避预算保存为连续 pending range，重新领取时依据实际空闲请求槽位成批取 whole-piece 前缀，不按每个 piece 人为拆分。

## 3. 动态分配算法

### 状态与原子性

查询可分配的连续完整 piece 区间 `[start, end)`，排除已完成、活动 lease、probe 预留与恢复区间。当前先用
available bitset 的连续 true run 定位候选，再按稀疏 runtime piece 边界切开；尚未引入额外区间索引，后续以测量决定。

请求槽位与 piece lease 分开计数，一个请求可持有多个 lease。已领取区间但尚未发送的请求也占用槽位。

一次 scheduler 锁内完成：读取槽位与区间、选择边界、签发全部 lease、更新占用状态。锁内不等待网络或 writer。若 permit 在外部管理，须定义预占及回滚协议，避免并发领取者重复预留或失败后泄漏占用。

### 当前实现：连续区间虚拟槽位与均衡份额

1. 计算包含当前领取者的待供给空闲请求槽位数 `S`，排除已经持有区间的请求。
2. 每个独立空闲区间先获得一个虚拟槽位；若区间少于 `S`，将剩余槽位分给当前字节份额最大的区间，并受 piece 数量和最小拆分长度约束。区间多于 `S` 时只纳入最大的 `S` 个区间。
3. 当前请求按所选区间的 `ceil(区间字节数 / 该区间虚拟槽位数)` 计算目标份额，再向 piece 边界取整。只有请求前后两侧都满足最小拆分长度时才主动拆分；天然短尾和独立小区间仍可领取。
4. 每次选择当前字节份额最大的区间，相同份额按起点排序，再按最大请求字节数和 64 lease 上限截断。硬字节/lease 上限优先；若上限内存在合法的最小拆分边界，则回退到不产生短尾的最近边界；若上限低于第一个合法边界，则保留硬上限并在诊断中记录冲突原因。
5. 虚拟规划只用于本次公平性计算，未领取部分保持可分配，下次根据最新状态重算；单一连续区间在顺序领取时趋近于 `剩余字节 / 空闲槽位`，不会固化一组临时 split。
6. 原子提交当前领取者的全部 lease；发送失败时按已有生命周期规则回收。

忽略 probe 与下载进度，64 MiB 连续区间、8 个空闲槽位可形成约 8 MiB 份额；2 个空闲槽位可形成约 32 MiB 份额。它们是示例，实际由区间、对齐和资源上限决定。

### 收尾与慢连接

- 仅当前槽位需要工作时，领取上限内的连续剩余区间，不为正在传输的同伴固定预留小片。
- 快连接完成后重新领取未分配工作，不直接偷取活动请求的 lease。
- 有限 Range 已发出后，不能本地改变终点并假定服务器同步改变。第一版只在发送前动态分配，不承诺活动大请求无缝二分。
- 持续慢请求沿用既有超时、慢速恢复和重复字节预算。更大区间可能放大长尾，必须验证。
- 如活动大请求成为主要瓶颈，另行设计未消费后缀转交或开放终点请求，明确 producer 停止、writer barrier、generation 切换与重复字节约束。

## 4. 实施顺序

### P0：诊断与可重现基线

扩展 [compare_public.py](../scripts/compare_public.py)、[analyze_public.py](../scripts/analyze_public.py) 和 [public_compare.rs](../examples/public_compare.rs)，接收模式及相关配置并保存有效值。

每次分配记录请求/worker ID、候选区间、候选槽位、截断前目标边界、待供给槽位、最终边界、截断原因和 lease 数。分别记录调度区间、线上 Range 与实际接收字节；完整候选份额表仅在 TRACE 输出，避免低日志路径付出诊断枚举成本。

记录响应头等待、body、writer barrier、请求间空闲、重试/恢复、重复字节、实际连接数和 socket 对端 IP。已增加首次多路 body 并行时间、达到 90% piece 完成至最终 writer flush、最后 body 完成至最终 writer flush 三项单调时间指标。响应头等待包含连接建立等成本，不全部归为服务端 TTFB。

交付：固定 4 MiB 基线可重现，短请求与空闲时段可解释。`public_compare.py --log-level trace` 用于诊断，`--log-level off` 用于低日志计时；两类轮次分开保存。

### P1：原子领取与独立请求槽位

建立一次加锁的普通请求领取接口，消除首片与扩批竞争。probe 单独预留并精确接管，恢复 lineage 保持独立。定义请求启动失败、取消和回收时的 permit/lease 状态转换。

交付：在固定模式下独立验证原子领取；不会因为一个请求包含多个 lease 而误判 HTTP 并发已满。

### P2：可选动态策略（主体已实施，均衡策略已补强）

实现第 3 节算法、配置验证与确定性诊断；当前使用连续区间虚拟槽位和均衡份额策略。沿用有限 Range 和 64 lease 上限，不同时扩大 probe。候选扫描利用 available bitset 的连续 run，候选不少于槽位时只选择最大份额而不完整排序；动态硬上限会在可行时回退最小拆分边界。恢复后缀复用连续 pending range，按实际空闲请求槽位批量重领。

交付：同一配置下，分配大小随文件、剩余区间和空闲槽位变化，日志可以复算其原因。

### P3：对照与默认策略决策

同窗口比较：现有固定 4 MiB、原子领取后的固定 4 MiB、固定 8/16 MiB、动态策略及 aria2。`compare_public.py --matrix` 在每个源、连接档位和轮次中随机交错 Fixed 4/8/16 MiB、Dynamic 与 aria2，并通过 `--log-level off` 和独立的 `--log-level trace` 轮次区分计时与诊断。用这些对照区分批次变大与分配策略的贡献。

默认策略已切换为 dynamic；Rust/Python 配置、示例及架构文档已同步，Fixed + `request_batch_size=4 MiB` 作为明确的兼容回退方式。公网样本仍需持续积累，不能把当前 CDN 结果解释为所有网络条件下的性能保证。

### P4：按证据推进后续优化

仅在测量显示瓶颈时考虑：扩大 probe 并支持多 piece 接管、减少批内 writer barrier、区间所有权与 lease 解耦、活动后缀转交或开放终点请求。各项单独设计、对照与验收。

## 5. 正确性与测试

所有未完成字节必须可解释为未分配、已分配或恢复中。普通请求不得重叠或遗漏。piece 与控制文件格式保持兼容；跨进程恢复只信任持久化完整 piece。

继续验证 200/206/416、Content-Range、总长度、编码、validator、截断和超长 body，保留既有回退语义。取消与恢复先停旧 producer，再等待 writer barrier，旧 generation 不得写入新 lease。

保持流式读取、内存预算和背压，不按整个 Range 分配 body 缓冲。worker 切换请求不重置重试、退避或恢复预算。

| 场景 | 核心断言 |
| --- | --- |
| 多 worker 同时领取 | 无重叠遗漏；首请求不拿走全部工作；槽位计数一致 |
| 1/2/4/8/16 槽位和不同文件大小 | 边界符合对齐、最小拆分与有效上限 |
| 区间多于/少于槽位、同长区间 | 结果确定；短尾可完成；不为凑并发过度拆分 |
| 完成 piece、probe、恢复后缀和非整片尾部 | 不跨受保护边界；probe 不丢弃或重复下载 |
| 64 lease 上限、固定 batch 为 0 或小于 piece | 资源边界生效；固定模式兼容 |
| 固定请求延迟、单连接变慢、中断 | 分别验证请求开销和长尾，恢复预算保留；中断后的连续后缀请求数量和长度分布不得退化为小于一个 piece 的批量 |
| 动态最大请求与 64 lease 截断 | 硬上限生效；存在合法边界时不制造短尾，无法兼顾时诊断记录最小拆分冲突 |
| Dynamic 明确启用时的大请求中断 | 只重试未确认内容，piece 边界和进度不重复计算 |
| Dynamic 明确启用时的取消恢复 | 旧 producer 停止后可从控制文件恢复并完成 |
| Dynamic 明确启用时的慢连接、低内存和慢 writer | 无死锁，背压不被误判为网络慢 |
| 取消、发送失败、暂停恢复、资源变化 | permit 与 lease 正确回收，无遗留占用 |

已扩展 scheduler 单测及既有传输/恢复集成测试，并补充 Dynamic 明确启用时的大请求中断、慢连接/背压和取消恢复覆盖；恢复中断测试已断言整 piece 请求长度和后缀重新成批。仍需执行完整 feature/绑定矩阵及 P3 公网/本地性能对照。

## 6. 性能门槛与交付

先用可控本地 HTTP 服务验证固定延迟、带宽差异和单连接变慢，再用多个公网源复测。覆盖小文件、约 64 MiB 和更大文件，以及 1/2/4/8/16 连接。各条件至少 10 轮，随机交错，保留失败样本。aria2 参数显式设置并保存完整命令。

报告中位数与四分位距、成功率、请求数、重复字节、启动和尾段时间、CPU 与峰值 RSS。逐轮验证哈希，适用时验证 ZIP CRC。保存构建版本、TLS 后端、有效配置和日志等级，不以历史公网结果直接作为发布门槛。

拟定采用门槛：

1. 正确性及产物检查全部通过，无新增不可解释的失败、死锁和资源泄漏。
2. 主要多连接场景争取较同时段固定 4 MiB 基线耗时降低 20%、请求数降低 25%；这是待验证目标，不是收益承诺。
3. 与固定 8/16 MiB 同场比较，证明跨文件大小或并发条件的收益；若收益仅相当于提高 batch，继续保留 Dynamic 的独立上下限与 Fixed 兼容回退，避免把某个 batch 值固化为新默认。
4. 单连接、小文件或资源受限场景耗时回退超过 5%，尾段耗时或峰值 RSS 增长超过 10%，必须解释并复测后决定是否采用。
5. 若瓶颈仍为响应等待、连接复用或 writer，依据诊断调整优先级，不持续放大请求上限。

交付顺序：诊断基线 → 原子领取与槽位模型 → 可选动态策略和测试 → 同窗口报告 → 默认策略及文档决策。第一版完成标准包括可解释的区间变化和兼容回退，不包含开放终点或活动区间抢占。
